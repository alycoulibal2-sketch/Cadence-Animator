## Video 81 — How to ACTUALLY Use VFX in Roblox (Develuper, 9:24) — 2026-09-12

Watched at `balanced` (92 frames read in full, all scene-change selections; near-static code/UI segments meant most of the 92 were code editor, Studio viewport or a "Top Charts" browse page rather than distinct motion). Transcript via captions, 235 segments.

Five entries written, all specific to concrete techniques shown or narrated, not restatements of "use VFX well": **attachment-anchored VFX with server-authoritative emit** (the video's foundational pair: an Attachment parents the effect to a moving part, and separately, only the server can make a fired effect visible to every player — two different problems solved by the same demo); **animation-marker-triggered VFX emit** (a named marker on the release frame fires paired sound+particles at that exact frame — this is almost exactly Cadence's own Part 39 timing envelope already, with this video's convention landing at `lead ≈ 0`); **raycast-derived impact VFX placement** (the impact clones to the actual raycast hit point, falling back to the aim target on a miss — the presenter calls this out by name as what "makes everything feel way more accurate"); **empty-rig-template as VFX organization scaffold** (a meshless rig used purely to hold folders of attachments/emitters, matched by part name onto a real character at spawn — Cadence has no analogue for "author once, name-match onto any rig" for effect bundles, only for motion via the library); and **ground effect slaved to an invisible proxy part** (an aura's ground ring tracks position only, not rotation, via a separate part someone updates every frame — directly a sibling of `W08-72`'s camera-slaved-to-proxy-part, same underlying idea applied to VFX instead of a camera).

What surprised me: how cleanly the video's own vocabulary (attachment = anchor, marker = trigger, "feels more accurate" = raycast placement) maps onto machinery `ai/vfxspec.js` already has (`anchor`, `timing.event`/`lead`, `EFFECT_ROLES`) — this is a confirming video more than a novel one, much like W01's result. The one clean *gap* it surfaces, twice, is the authoring/runtime boundary: a raycast hit point and a live-updated ground proxy are both **runtime-computed positions with no keyframed representation**, and Cadence's current model (an authored `.cadence` project, no physics, no per-frame recomputation against another object) simply cannot represent either — correctly recorded as "not applicable" rather than invented as a measurement.

Nothing here contradicted an existing knowledge card. No capture candidates — the only "character" on screen is a static-posed R6 robot; no walk, attack or landing worth a reference clip. No new check queued: the one obviously-relevant measurement (`vfx_timing_alignment`, marker-vs-effect-peak distance) is already built (VFX-010) and this video's use of it is a confirmation, not a gap.

## Video 82 — How to Learn Roblox Aura VFX in 1 Hour (Twist VFX, 41:47) — 2026-09-12

Watched at `transcript` only (1131 caption segments), deliberately — a single continuous live-build screen recording where every technique is narrated with exact property names and values as it happens; no frame pass was needed to confirm any of the six entries below, all of which quote the transcript's own precise language. This is the closest thing so far in the whole watchlist to a straight Roblox ParticleEmitter property reference, but the entries below are the specific TECHNIQUES buried in it, not the property list itself (rate/lifetime/speed/spread/shape/flipbook/etc. are Roblox API surface, not craft knowledge, so they were not written up as cards).

Six entries: **phase-offset dual emitters for a persistent glow** (two identical low-rate emitters started half a lifetime apart so their fade cycles sum to roughly flat — the single most sophisticated technique in the video, and a clean case where Cadence's VFXSpec, one emitter per compiled effect, has no field for "a second copy of this at a declared phase offset"; that composition is PNX's job, not VFXSpec's, by the same boundary decision already in the code); **concurrent particle budget = rate × lifetime** (a high rate is not itself spammy if lifetime is short — directly legible against Cadence's own `EFFECT_ROLES` budget-share caps, though VFXSpec does not expose rate/lifetime as separate dials to multiply); **simultaneous-activation baseline defeats authoring-order phase drift** (emitters toggled on at different times while building drift out of phase purely by accident; disable-and-re-enable-together before judging the result, since the real game always activates everything at once — and Cadence's declared, frame-numbered `timing.event` is structurally immune to this exact class of bug, worth recording as a case where the authored/keyframe-native model sidesteps a live-toggle workflow's own failure mode); **per-instance randomization breaks a unison look** (the comma min,max convention on rotation/speed/lifetime, named as a cheap, high-value fix); **a particle must fade at both lifetime extremes or it pops** (near-universal, presenter says he sees it violated constantly); and **a speed floor of 0.001, never a literal 0**, to dodge an orientation-mode clipping bug the presenter can trigger reliably but cannot fully explain.

What surprised me: the phase-offset glow trick is the first technique in this whole watchlist that is a genuine COMPOSITION problem (two synchronized-but-offset emitters) rather than a single-emitter authoring choice — it lands exactly on the VFXSpec/PNX boundary the codebase already draws for other reasons (layers, multi-node graphs), which W08's own throughline flagged from a different angle (Cadence's two systems not always agreeing on scope). Also notable: the simultaneous-activation entry is a rare case of Cadence's data model being *structurally better* than the live-authoring workflow being taught, purely as a side effect of storing timing as declared frames rather than wall-clock toggle history — worth keeping in mind as a positive selling point, not just a gap list.

Nothing contradicted an existing knowledge card (there was no prior card to contradict in this territory — VFX/particle craft is new ground for this corpus, W09 being the first VFX-heavy batch). No capture candidates (a screen recording of Studio's UI, not a performed character motion). No new check queued: none of the six entries above name a quantity `ai/motion.js` could measure from project data — they are either particle-system-internal (outside Cadence's rig/item motion model entirely) or authoring-workflow habits, and are recorded as `not applicable`/`not measurable in this build` rather than stretched into an invented check.
